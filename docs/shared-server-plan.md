# Shared multi-board `serve` plan

Status: proposed. This document specifies a follow-on to the local editor; it does not describe behavior implemented on `main` today.

## Goal

Run one local Trackerboard service for all boards in a user's configured data universe. Agents and harnesses can start or reuse that service, while a browser index and board-specific URLs let the user move between boards. A board remains independently backed by JSON, SQLite, or GitHub Projects; serving multiple boards does not combine or copy their data.

The service stays local to the user's machine and binds only to IPv4 loopback. It is not a cloud service, a team-wide server, or a replacement for the CLI. Starting it after a reboot discovers existing board state from disk and backend configuration; it does not recreate boards or migrate them.

## Current baseline

Before this work, `serve` resolved one board name, loaded its backend, and started one editor server. The editor already used validated command-shaped operations, a capability URL, bearer authorization, exact Origin and Host checks, expected revisions, and two-second snapshot polling. The shared implementation extends those contracts; it does not add whole-board replacement. The implementation and tests are in [the backend command](../skills/trackerboard/scripts/commands/backend.mjs), [the editor server](../skills/trackerboard/scripts/lib/serve.mjs), [the editor callbacks](../skills/trackerboard/scripts/lib/editor-operations.mjs), and [shared server tests](../test/shared-server.test.mjs).

Board discovery is a synchronous scan of `TRACKERBOARD_HOME/boards`. Backend selection currently depends on the working directory's repository binding key; SQLite paths use that key, while the GitHub Project pointer is in the board's local index. A shared process cannot safely infer a board's target from the directory that happened to launch it. Pinning one storage target per board is therefore a prerequisite, not a detail to defer to the server implementation.

## Review closure

The multi-board design review is resolved in the decisions and delivery gates below; these points are requirements, not implementation-time choices. Backend opening uses the saved binding root and repository identity, branch bindings alias one canonical repository target, and unbound boards use global plus board-local configuration only. Duplicate routes are detected by concrete backend-record identity. Board capabilities survive rescans and temporary outages, while removal revokes the route with `410`; backend polling and GitHub caching are specified separately. A lifetime OS lock is distinct from storage mutation locks, and the authenticated control channel alone can return scoped URLs. The protected index is intentionally an all-board grant. Discovery is bounded, failed backends back off independently, and removal drains or rejects writes under the storage lock.

## Decisions

### Board identity and backend target

- Add a stable `boardId` and canonical `storageBindingKey` to each board's existing `.local.json` index. Assigning an ID to a legacy board must not change its canonical board JSON or silently change its selected backend. Keep bindings as aliases for resolving a board from worktrees and directories. Do not put backend metadata in canonical board JSON.
- Each board has exactly one active backend target. Creation and successful migration pin the key used for that target. For Git repositories, derive the canonical repository key from the Git common directory with a null branch; branch-specific binding keys remain aliases, not backend-config keys or separate server targets. All worktrees and branch aliases for the same Git common directory therefore resolve to the same target. Bindings for different repository roots are distinct candidates. If a board has no pinned target and multiple roots/stores could select different targets, require an explicit choice; never fall back to `bindings[0]`.
- Persist enough non-secret target context in the local index to open the backend without the server's current working directory: the canonical binding key, selected binding's repository root, and normalized, credential-free repository identity/URL where applicable. Refactor `openBackendFor` to accept this explicit target descriptor and pass that saved root/identity through as its repository context. It must not infer `repoRoot`, `repoUrl`, or a repository config key from the daemon's CWD. A missing repository root must not prevent access to a GitHub Project when the saved Project pointer and repository identity are available. Strip URL credentials, query strings, and fragments before persisting repository identity.
- Keep existing board-name uniqueness and file paths for compatibility. Use `boardId`, not the display name or current directory, for server routing and in-memory registry identity.
- Preserve configuration precedence: global config, config for the board's canonical repository key, then the board's local override. Branch-specific bindings are aliases, not separate shared-server targets: normalize them to the repository-wide canonical key before resolving repo config, so the server does not arbitrarily select `bindings[0]` or expose duplicate branch routes. If aliases point to divergent roots or stores and no canonical target can be established, mark the board `needs-binding` instead of choosing one. The resolved backend and target are read from the local index plus those configuration layers.
- For legacy JSON boards, the JSON file remains authoritative and can be registered without consulting the launch directory. Assigning `boardId` or target metadata must not change its content or backend selection. For a migrated board, reuse an unambiguous saved target. If legacy bindings or backend stores yield multiple possible targets, do not guess or merge them: show a `needs-binding` state and require an explicit selection. `trackerboard backend --set-binding <key>` selects an existing saved binding alias, normalizes it to the canonical repository key, opens the board at that current-backend target, and reads and validates it before persisting the new pointer. It does not copy, merge, create, or migrate data. Reject unknown aliases or unreadable/missing targets without changing the local index. If an orphaned legacy board has no saved binding for its old inferred target, require the user to add the intended binding explicitly before selection; never silently open an empty default target.
- `trackerboard migrate --binding <key>` selects the destination binding only. The source is the currently pinned active target; if it is ambiguous, the user must select it first with `backend --set-binding`. Dry-run output names both source and destination. Keep the source active on dry-run, failure, or failed read-back; switch the active target only after the destination has been read back and validated. Do not interpret `--binding` as an implicit source selector.
- Migration preflight must detect split or divergent SQLite stores before pinning a key. GitHub state is associated with its one saved Project pointer. Ambiguous or unreadable state remains untouched until the user chooses a target.
- A board with no repository binding uses global configuration plus its board-local override, with no repository-scoped config, repository URL, or launch-directory context inferred. JSON remains available. An unbound SQLite board must provide an explicit `sqlite.path`; do not derive it from the daemon's CWD or a missing binding key. A repository-dependent backend such as GitHub Projects requires an explicit binding or a previously saved repository identity and Project pointer before it can be opened or bootstrapped.
- Define duplicate-store detection by the concrete backend record, not by binding key: JSON uses its normalized absolute data-file path; SQLite uses the normalized absolute database path plus its row key (currently `board.name`, because multiple board names in one SQLite database are supported); GitHub Projects use the Project node ID. Normalize symlink aliases to the same existing target, and resolve non-existing paths through their canonical parent directory where possible. Two board IDs collide only when their complete backend record identity matches. If they collide, mark both as requiring repair and do not mount duplicate editable routes. Pending GitHub bootstrap targets remain provisional until a Project node ID is saved, then are checked for collisions before phase data is written.
- Preserve legacy `create --no-bind` safety. Older versions could resolve a repo-scoped SQLite/GitHub target from the launch CWD before creating an unbound board. If that target cannot be reconstructed from saved metadata, classify the board as `needs-binding`; do not reinterpret it as a new global/default target and create an empty board there.

### One service process and its lifecycle

- `trackerboard serve` becomes an ensure-or-reuse command. If no service exists, it starts a detached local server process, waits for its authenticated health response, performs discovery, and prints the index URL. Detaching means the first agent's shell can exit without taking the service away from other agents or harnesses.
- `trackerboard serve --board <name>` ensures the same service, requests a rescan, and prints that board's URL. Without `--board`, it also prints the URL for the board resolved from the caller's working directory when one exists. Keep the existing `ok: serving NAME at URL` output line for that selected board, and add an `index:` line. With no selected board, `serve` still starts or reuses the service and prints the index.
- Add `trackerboard serve status` and `trackerboard serve stop`. Stop asks the authenticated service to exit and waits for its lock to be released. `serve --foreground` is available for debugging and tests; it does not create a second instance if the detached service is already running.
- Scope singleton identity to the canonical real paths of both `TRACKERBOARD_HOME` and `TRACKERBOARD_DATA_HOME` (including the effective XDG defaults). Different data/config universes are separate services. A second invocation requesting a different port from the running service fails with the current address; it never starts a second server silently. If the requested port is occupied by a process that does not prove the expected instance nonce, report a port conflict rather than attaching to it.
- Hold a cross-process OS lock for the service lifetime in a user-private runtime directory, separate from the backend's shorter read-modify-write lock. The service must never hold the storage lock for its lifetime. The service lock primitive must be released by the OS when the owner exits; do not implement singleton ownership as a PID-only stale file. A mode-`0600` runtime record in a mode-`0700` directory contains the instance ID, process metadata for diagnostics, address, and a random control capability. It contains no index or per-board browser capabilities. A second CLI invocation reads that record and authenticates to the control endpoint with the control capability before requesting status, rescan, or URLs. The endpoint must never return capabilities or tokenized URLs to unauthenticated callers; authenticated URL lookup returns the index URL or only the explicitly requested board URL. PID is informational, never proof of liveness. If the lock is held but authenticated health fails, fail closed and explain how to inspect/stop the owner; do not start another listener.
- Runtime capabilities are per service run and never enter board data, backend configuration, or logs. After reboot the OS lock is gone; the next `serve` call cleans stale runtime metadata only after acquiring the lock, scans durable board indexes, and creates fresh capabilities. Automatic launch at login/reboot is explicitly out of scope.

### URL and board discovery contract

- Use `http://127.0.0.1:<port>/i/<index-capability>` for the index and `/b/<boardId>/<board-capability>` for each board. A request without a valid capability gets no board listing; do not expose tokenized board links from an unauthenticated `/` route. The authenticated control endpoint returns the index URL to CLI callers and returns a board URL only after the caller explicitly names a board.
- The protected index lists all discovered boards and their display title/name, active backend type, and sanitized availability state. It links to each board's capability URL. This intentionally makes the index capability an all-board access grant: anyone who obtains it can discover and open every listed board. The separate board capabilities still protect direct board URLs from callers that do not have the index. If per-board compartmentalization is later required, the index must stop exposing board bearer URLs and route access through a separately authorized mechanism.
- The service scans the local board index, not the current working directory. It can therefore serve all boards after restart even when the launching directory has no board binding. Duplicate target detection uses the concrete target identities above; collisions are visible as errors for every affected board, never silently collapsed.
- Run automatic discovery every ten seconds so newly added/removed boards become visible within a bounded interval. A CLI-triggered rescan may run immediately, but concurrent requests share one scan and full scans are rate-limited to at most one every two seconds. Local data snapshots continue to poll every two seconds independently of discovery; discovery itself must not trigger per-board GitHub reads.
- A second `serve` call asks the running process to rescan before resolving an explicit board or current-directory binding. It obtains the index URL, or the URL for an explicitly named `--board`, only through the authenticated control endpoint; unauthenticated health/status requests never disclose either URL or any browser capability. If `--port` is supplied and differs from the running instance's port, return an error containing the current address rather than silently reusing a different port or starting another listener. Unknown boards return a clear not-found result without stopping the service. A request for a newly created board can therefore find it without restarting the service.
- Keep a board's in-memory index and board capabilities stable across rescans while its `boardId` and concrete target identity remain unchanged. Rotate capabilities only when the service restarts, the board is removed and later re-added, or its backend target is rebound/migrated. A temporary backend outage does not revoke the URL: show a sanitized unavailable state, keep the route, and let the same URL recover when the backend returns. On board removal, revoke the route and return 410 for its old URL. A backend migration or binding change replaces that board's adapter/cache and rotates its board capability; open pages receive a reload/revision-conflict response. Name/title changes do not change the route identity.
- Use a cross-process mutation lock per board, shared by CLI and editor writes; keep the existing global lock for operations that truly span boards. A slow GitHub mutation must not block writes to another board. Once removal is observed, mark the route as draining and reject new writes. A write already inside that board's lock may finish before removal; if removal obtains it first, a later write must re-check the board's existence/target under the lock and fail without recreating it. Removal is not complete until prior writes have drained, and the old URL returns 410 afterward.

### Backend, editor, and PR behavior

- Keep one cache and adapter lifecycle per board. Load boards lazily and isolate synchronous backend work in a per-board worker process so a slow or unreachable GitHub Project cannot delay startup, periodic discovery, or another board's JSON/SQLite requests. Display sanitized per-board failures and retry that board independently with capped exponential backoff (starting at two seconds, capped at 60 seconds, with jitter); reset backoff after success and rate-limit repeated logs to state changes or periodic summaries.
- Poll local JSON/SQLite snapshots and local indexes every two seconds, preserving visibility of CLI writes. Discovery and index rendering use cached backend metadata and never contact GitHub once per board on each scan. Discovery acquires each board's mutation lock non-blockingly; when a board is busy, retain its last discovered route/identity and retry on the next bounded scan. After acquiring a lock, recheck that the board still exists before writing identity metadata, so a stale name captured by `listBoards()` cannot resurrect a removed board. Coalesce GitHub reads per board and refresh remote state at most once per 60-second cache window; concurrent requests share one in-flight refresh. GitHub CLI calls have finite configurable deadlines, and worker RPCs have a longer bounded deadline; timeout fails and restarts only that board's worker. Publish route changes before asynchronously retiring old workers so a batch of slow closes cannot stall discovery. GitHub pages may be unavailable while `gh` or the Project is unreachable without taking down the service.
- Reuse the current editor's validated board operations for board details, wave/phase CRUD, dependencies, and log entries. All editor writes pass through the active backend and the same per-board read-modify-write lock as CLI writes. Local JSON/SQLite writes compare expected revisions. For each GitHub mutation, reread the latest Project state, compare it with the client's observed version, and apply the command-shaped operation only to affected fields/items; do not rewrite the entire cached board over newer remote data. If the change is already visible, or the command's target changed incompatibly, return an observed-conflict response with a fresh snapshot. A retry must reread and reconcile stable phase-ID/item-ID mappings. Browser log appends carry a stable operation ID and durable receipt so a partial GitHub write can be retried without duplicating the entry; retain the newest 100 receipts per board. Invalidate cached GitHub snapshots after failed remote saves. GitHub has no transaction or compare-and-swap, so a same-field race between the final read and write remains best-effort last-write-wins across machines; report this limit rather than claiming strict concurrency control. Never accept an arbitrary whole-board PUT.
- Preserve phase status as human/agent-controlled. PR lifecycle remains a derived badge only: Draft is todo-colored, Open is active-colored, Conflicting is blocked/red, Merged is done/green, and Closed-unmerged is dropped/gray. Only merged PRs are green; a merge never advances or closes a phase.

### Security boundaries

- Bind the page listener to `127.0.0.1` only. Apply exact Host validation and, for browser writes, exact Origin validation plus the board bearer capability. The CLI control capability is separate from browser capabilities and is accepted only by control operations; it cannot write board data.
- Require the user-private runtime directory and permissions before starting. Write runtime state atomically and remove it only while holding the singleton lock. Do not log capability URLs or request authorization headers.
- Preserve no-store, no-referrer, nosniff, a restrictive Content Security Policy, and frame denial. Escape board names, titles, and errors in the index. Do not render raw backend errors, local filesystem paths, repository-private metadata, or credentials to the index.
- Keep all HTTP routes on loopback and validate the Host header to reduce DNS-rebinding risk. Do not add CORS access for arbitrary origins.

## Delivery phases

### Phase 1 — Pin identity and target resolution

Add `boardId`, `storageBindingKey`, and the saved backend target context to local indexes; make new boards and migrations pin them; and refactor backend opening to use that context rather than process CWD. Specify that branch bindings are aliases of the canonical repository-wide key, that unbound SQLite requires an explicit path, and that `--set-binding` only validates/selects an existing alias while `migrate --binding` names the destination. Define legacy `create --no-bind` recovery, the no-repository-context rule for unbound boards, and concrete backend-record identities (including SQLite path plus board-name row key). Keep JSON default behavior and existing CLI commands compatible. Before proceeding, tests must cover legacy JSON compatibility, worktree and branch aliases, divergent roots and stores, CWD-independent backend opening and credential-free repository identity, unbound-board config resolution, explicit unbound GitHub context, config precedence, selected-target read-back and no-copy behavior, destination-only migration selection, dry-run/failure source preservation, the SQLite path-plus-row-key collision matrix, target collision detection, and refusal to guess between divergent or orphaned legacy stores.

### Phase 2 — Shared process manager and index, JSON first

Implement the private runtime directory, lifetime OS lock, authenticated nonce/control channel, daemon startup/stop/status, port mismatch behavior, protected index URL, and board URL/capability routing. Initially register JSON boards only. Preserve the existing editor command protocol and one-board output compatibility. Tests must cover concurrent first starts, attach/reuse, stale runtime records, PID reuse with a mismatched nonce, bad port ownership, runtime permissions, absence of browser capabilities from the runtime record, no URL disclosure by unauthenticated control requests, authenticated scoped URL lookup, separate home/data universes, discovery and explicit-rescan bounds/coalescing, token stability across rescans and outages, unavailable-target recovery, the index's all-board capability scope, and service exit cleanup.

### Phase 3 — Multi-board registry and backend isolation

Discover additions/removals and backend/config changes without restarting. Add lazy per-board worker/adapter creation, cache invalidation on migration, token revocation, and isolated unavailable states. Enable SQLite and GitHub Projects after the canonical target contract is in place. Tests must cover multiple simultaneous boards across all backends, independent failures and capped retry backoff, slow GitHub reads and writes not blocking local boards or discovery, per-board write serialization across CLI/editor, nonblocking discovery while a board lock is held, stale-list removal without identity resurrection, asynchronous worker retirement, finite GitHub/worker deadlines and per-board recovery, no GitHub request per index rescan, CLI writes visible in the editor, stable capabilities across scans and outages, removal/re-addition, removal racing an in-flight write, duplicate target identities (including two names in one SQLite file as distinct rows, the same path-plus-row-key as a collision, symlink aliases, and duplicate GitHub Project IDs), unresolved multiple-root candidates, observed GitHub conflict responses with fresh snapshots, durable log-append receipt behavior after a partial write, and migration while the service is live.

### Phase 4 — Editor integration and security hardening

Mount the existing editor page under board-specific routes and expose only validated command operations. Add index and board page security headers, Host/Origin/capability tests, stale-revision tests, sanitized error rendering, and behavior for unknown or unavailable boards. Verify that an unauthenticated request cannot list boards, that the index capability intentionally exposes all board URLs, and that a board capability alone does not expose other boards. Confirm phase status remains unchanged when a linked PR merges.

### Phase 5 — Acceptance, docs, and rollout

Document URL/lifecycle behavior, runtime storage and permissions, port conflicts, backend identity, legacy repair, reboot recovery, and the fact that login auto-start is not included. Run the full test suite, then use a disposable private GitHub Project to verify the three backends, cross-board isolation, a server restart, a migration while serving, a slow/unavailable Project alongside a local board, and token expiry after stop/restart.

## Completion criteria

- One invocation serves every unambiguous board in the configured data universe, and concurrent invocations reuse that instance rather than starting duplicates.
- The same board resolves to the same backend target from every worktree alias and after reboot.
- New, removed, migrated, or unavailable boards affect only their own route and cache; local CLI edits appear without restarting the server, unchanged targets retain their capabilities across scans, and removal cannot race a write into recreating deleted board data.
- The browser editor cannot bypass board validation, revision handling, backend locking, loopback binding, capability checks, or Origin/Host validation.
- Existing single-board CLI usage and the JSON default remain compatible, and PR merges never mutate phase status.
