# trackerboard

Trackerboard is a CLI-first, harness-neutral tool. JSON is the default backend, stored under `~/.trackerboard/boards/`; SQLite and private GitHub Projects are explicit opt-ins. The Claude artifact integration is optional. **Never read, regenerate or hand-edit a rendered page to change board data.** Use the CLI.

Run the CLI as `trackerboard …` if it is on PATH, otherwise `node <this skill's base directory>/scripts/trackerboard.mjs …`. `trackerboard help` prints the full usage.

## Which board

`--board <name>` is optional. Without it the board resolves from the cwd: the git repository (any worktree of it) or directory a board was bound to at `create` (or with `bind`). A board bound with `--branch` wins over a repo-wide one on that branch. If more than one board resolves at the same level the command fails and lists them; pass `--board`. `TRACKERBOARD_BOARD=<name>` also selects one.

## Writing

```
trackerboard create <name> --title "…" [--repo-url https://github.com/org/repo] [--branch] [--no-bind]
trackerboard insert --phase P0.1 [--wave W] --title "…" --status todo --deps P0
trackerboard update --phase P0.1 --status done --pr "#2933" --note "merged 951de27" --log "P0.1 merged"
trackerboard delete [--wave W] P0.1
trackerboard insert --wave B --title "Wave B" --prefix B-        # waves: insert/update/delete without --phase
trackerboard update --title "…" --lede "…"                       # board fields: no --phase/--wave
trackerboard dep add F7 --on F1,F2 | dep rm F7 --on F2 | dep set F7 --on F1 | dep clear F7
trackerboard log "JR ruled the EXCLUDED sites"
```

- Phase fields: `--title --lane --owner --status --note --req --issue --pr --review --notes --deps`. `--issue` is a reference to an existing GitHub issue (`#1234` or `1234`); trackerboard does not create repository Issues. `--owner` is who is working the phase (your agent id, or a person); set it when you start and clear it with `--owner ""` when you hand it off. `--note` is the one-line status detail; `--req`, `--review` and `--notes` are expandable detail. Text fields are CommonMark markdown (rendered by markdown-it); write markdown, not HTML.
  - Everywhere (titles, `--note`, log messages, PR and issue cells, the expandable fields): inline markdown — `` `code` `` (use ``` `` a`b `` ``` when the code holds a backtick), `**bold**`, `*italic*`, `[text](url)`, `https://` URLs (autolinked) and bare `#1234` (linked to the board's `--repo-url`: PRs in the PR column and elsewhere, issues in the Issue column). Put identifiers, commands, file paths, env vars and flags in backticks so they render as code.
  - In `--req`, `--review`, `--notes`, wave and board notes and the lede, also block markdown: paragraphs, headings, `- ` and `1.` lists, `>` quotes, tables and fenced code blocks for multi-line commands or output. A single newline is a line break.
  - HTML `<code>…</code>` and `<strong>…</strong>` are converted to backticks and `**` when written; any other HTML shows as literal text.
- Status: `todo active review waiting blocked done ongoing external dropped` (aliases such as `merged`, `in-progress`, `not-started`, `n/a` are accepted).
- Long values: `--req @file.md` reads a file; `--notes -` reads stdin.
- `--wave` is optional. A new phase goes to the wave of its parent id (`P0.1` → `P0`'s wave), else the wave whose `--prefix` matches, else the wave holding the same id stem, else the only wave.
- Position comes from the id: `P0.1` / `P0-1` lands right after `P0` (and after lower siblings like `P0.0`) even if `P1` exists. Insert never overwrites; it fails if the id exists anywhere on the board.
- Import an existing board JSON with `trackerboard import <name> --from file.json`. A board generated by a project script is refreshed with `import --from file.json --replace [--keep owner]` (format: `board.schema.json`), and `trackerboard github [--dry-run]` fills PR/Issue references from PRs and issues that mention phase ids. It does not change the human-controlled phase status. Never hand-edit a generated board's fields that the generator owns; the next import overwrites them.
- Rename with `update --phase X --rename Y` (dependencies follow). Move with `--to-wave W`.
- Deleting a phase removes it from every other phase's deps and says which.
- Add `--log "…"` to any write to record it in the board's "Recent changes" (keeps the last 40).

## Staying in sync

For every backend, read with `trackerboard show` before work and make changes through the CLI. GitHub rereads and reconciles before narrow writes, but its concurrency protection is best effort because GitHub does not provide compare-and-swap for these updates. Coordinate simultaneous writers and inspect the board after concurrent changes.

For a board linked to a Claude artifact, other agents may publish at any time. The CLI tracks the published version and won't let you write from a stale copy. Run `trackerboard refresh` before reading or writing that linked board.

**Refresh a linked Claude artifact:** `trackerboard refresh` prints an `ArtifactData get` call. Make it, then run the printed `trackerboard pull --version <version from the result>`.
- If nothing changed, `pull` does nothing.
- Otherwise it merges the published board with unpublished local changes. Conflicts on the same field stop the pull; ask which value to keep, then rerun with `--theirs` or `--ours`.

Writes to a linked artifact are refused if it has not been checked within 120 seconds (`TRACKERBOARD_FRESH_SECONDS`). A `synced` counts as a check, so a batch of writes made after refresh or publish goes straight through.

## Backends and migration

Backend config is machine-local and resolves key-by-key from global config to repository config to a board override. Defaults are `~/.local/share/trackerboard/config.json` and `~/.local/share/trackerboard/repos/<bindingKey>.json`; board-specific metadata and its override are in `~/.trackerboard/boards/<name>.local.json`. `XDG_DATA_HOME` or `TRACKERBOARD_DATA_HOME` changes the config root, and `TRACKERBOARD_HOME` changes the board-data root. The default backend is `json`. A configured backend selects the default for new boards and is pinned in their local metadata; changing defaults does not move existing boards. Legacy JSON boards without a pointer stay on JSON until migration verifies another backend. SQLite stores a per-repository database at `~/.local/share/trackerboard/repos/<bindingKey>.sqlite`, unless `sqlite.path` is set. It is durable local storage, not cross-machine coordination. Select a backend through these JSON settings or by migrating; `backend` is for inspection only.

```text
trackerboard backend [--json]
trackerboard migrate --to json|sqlite|github [--dry-run]
trackerboard serve [--board NAME] [--port N]
trackerboard refresh-prs [--repo OWNER/NAME] [--limit N]
```

`backend` reports resolved configuration and active storage; it does not switch storage. `migrate` first writes a mode-0600 recovery snapshot under `~/.trackerboard/recovery/`, copies to the target, reads it back, validates it, and changes the active override only after verification. If a migration fails, the source backend remains active. Moving JSON to SQLite or GitHub leaves the JSON file as an inactive recovery snapshot. Moving back to JSON exports current active data and never restores stale snapshot contents. Migration detaches a linked Claude artifact without deleting or changing it. The old artifact remains a read-only snapshot, and `page`, `link`, `push`, `refresh`, `pull` and `synced` are unavailable after migration.

Select `backend: "github"` before creating a board, or migrate an existing board. Bootstrap creates a generic Project, immediately sets it PRIVATE, and verifies that state before writing board data. If privacy cannot be verified, Trackerboard attempts to delete the still-empty placeholder and stops with permission guidance. The owner is derived from the repository remote or board `repoUrl`; the Project pointer and stable board ID are kept in local metadata. No token is requested, logged, or stored. Phases are Project draft items, not repository Issues. GitHub cannot hide a repository's Issues; this backend avoids creating any and stores the phases only as private Project draft items.

Use `gh >= 2.96.0`, Project read/write permission, and the OAuth `project` scope; add the scope with `gh auth refresh -s project`.

The Project fields are Trackerboard ID, Status (the nine phase statuses), Wave, Lane, Owner, and Order; draft-item title is the phase title. The versioned item-body block stores phase note, req, issue, pr, review, notes, and deps. A versioned Project README metadata block stores board fields, ordered wave metadata, the recent log, stable board ID, and the phase/item mapping. The README metadata block and each item-body block have independent 60 KiB limits. Oversized writes fail; text is never truncated.

`serve` exposes an editable local browser view over the active backend. It binds only to `127.0.0.1`, uses a random per-run capability URL and requires a bearer token plus same-origin validation for writes. It sends validated board operations, not a whole-board replacement. JSON/SQLite changes appear on the next two-second poll; GitHub state is cached for up to 60 seconds. `refresh-prs` refreshes derived PR badges with a 60-second cache: Draft=todo color, Open=active, Conflicting=blocked/red, Merged=done/green, Closed-unmerged=dropped/gray. PR lifecycle badges are independent of phase status; a merge updates the badge but never the human-controlled phase status. Green means merged only.

## Publishing

Every write to a linked Claude artifact ends with:

```
publish: ArtifactData {"action":"set","url":"…","collection":"board","doc_id":"state","file_path":"…/out/docs/<name>-<hash>.json","if_version":7}
then:    trackerboard synced --board <name> --version <version from the result> --doc …
```

The document includes the dependency-graph layout (computed with ELK by the CLI); the page only draws it. If the CLI warns that the layout was skipped, run `npm install` in the trackerboard repo; the publish still works.

Make exactly that `ArtifactData` call (load the tool with ToolSearch `select:ArtifactData` if it is deferred), then run the `synced` line with the `version` from the result. The page updates live for anyone viewing it. Batch several writes, then publish once: only the last write's steps matter.

- **Refused for a version mismatch:** someone published in between. Run `trackerboard refresh`, make its `get` call, and run `pull`. That merges your changes onto theirs and prints a new publish step; make that call. Nothing needs to be redone.
- **No `if_version` printed, and the write is refused because the document exists:** do the refresh steps, then `trackerboard push` and retry.

Commands on one machine take a lock (`~/.trackerboard/.lock`), so agents sharing a machine never lose each other's writes.

**First publish** (a new board, or an old hand-written tracker being replaced): run `trackerboard page`. It writes the page and prints the `Artifact` publish call with the `db` capability. Make that call, then `trackerboard link --url <artifact url>` and `trackerboard push`, and make the printed `ArtifactData` call. After publishing, the page HTML only needs republishing when this skill's page template changes (`trackerboard page` prints that call too).

## Reading

`trackerboard show` prints a compact board grouped by wave and lane (`lane A  4/10 done`), one line per phase: id, status, title, deps, `@owner`. It ends with the phases whose dependencies are all done. `show --phase X` prints one phase in full, including its lane, and `show --json` prints the raw data.

Narrow any of these with `--wave W`, `--lane L`, `--status S[,S]` and `--owner O`. Matching ignores case; `--lane ""` and `--owner ""` match phases with none. Two terse views print only rows:
- `--ids`: one phase id per line.
- `--pr-list`: id, status and PR for each phase that has one.

For example, `show --lane B --status blocked --ids` or `show --lane A --pr-list`. `dep list X`, `dep ready` and `dep graph` (mermaid) cover the graph. Prefer these over opening the artifact.
